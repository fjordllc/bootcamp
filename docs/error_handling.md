# エラー処理と通知

初めて変更する人向けの短い判断基準です。Railsでの具体的な扱いは[Railsのエラー処理](rails_error_handling.md)を参照してください。

## まず3種類に分ける

| 分類 | 意味 | 扱い |
| --- | --- | --- |
| Expected / Accepted | 許容される正常な結果（通常は2xx） | 通常処理として扱う。個別通知しない |
| Expected / Un Accept | 起こり得るが処理は失敗した状態（明示的な4xx・5xxなど） | 失敗を表す値や特定例外だけを扱い、必要な回復・記録を行う |
| Un Expected | 想定していない不具合・状態 | 原則として握りつぶさず伝播させ、自動報告に任せる |

分類はステータスだけでは決まりません。JSON検証サービスが入力の「無効」をHTTP 200と`false`で返すなら、それは許容される判定結果なのでExpected / Acceptedです。一方、登録APIが不正なJSONをHTTP 400で拒否するのはExpected / Un Acceptです。Acceptedは「望んだ成功」だけでなく「許容される結果」を指します。エラーの存在を知っていることや、rescueを書いたことだけでExpectedにはなりません。

## 通知には対応者の行動が必要

これはBootcampの運用方針で、Rails共通の規則ではありません。

- **critical**: 直ちに対応が必要。
- **error**: 操作・設定の失敗や不整合が実際に起き、修正または復旧が必要。
- **warning**: 異常の調査や判断が必要。warning以上は必ずトリアージする。すべてが緊急対応やコード修正を意味するわけではない。
- **info / debug**: 個別対応やアラートが不要な記録。

通常の入力検証失敗や404は、通常それだけでトラッカーに登録しません。不要な通知と判明した場合も、理由を記録してフィルターや閾値を見直します。理由を確認せず同じ項目を習慣的に無視し続けないでください。

通知は新規発生、解決後の再発、閾値を超えた増加で行い、同じ原因の反復を毎回通知しない運用を基本とします。原因をまとめつつ、発生回数と影響対象は残します。未解決項目を定期的に確認し、担当者を決めてください。一時的に起こり得る失敗の頻度や、後から調べる記録はログ・メトリクス・保存先で扱い、件数急増には閾値アラートを使います。

この運用例の背景として、[gifteeの事例](https://tech.giftee.co.jp/entry/2020/10/16/150000)は新規・再発等に絞った通知と日次確認を、[stmnの事例](https://tech.stmn.co.jp/entry/2024/02/13/093103)は通知閾値や定期運用を紹介しています。いずれも各社の事例であり、唯一の正解ではありません。

## エラー監視ツールを用途で使う

[発表スライド](https://speakerdeck.com/morihirok/hun-dun-tositali-wai-chu-li-toerajian-shi-nizhi-xu-womotarasu)の43枚目はUnexpectedを処理しない考え方を示し、67〜73枚目はUnexpectedを捕捉して報告後に続行する設計を避けています。76〜79枚目はExpectedのログ用途にトラッカーを使わず、頻度監視にはAPM（Datadog / New Relicなど）、後日の分析にはDB・検索用ストレージ（S3 + Athena / BigQueryなど）を使う考え方です。

Bootcampでは通常、伝播したUnexpectedを既存のRollbar連携で自動報告します。捕捉して再送出しないコードでは自動報告されないため、報告が必要なら明示します。すでに伝播する例外を手動でも報告して二重登録しないでください。

## Bootcampの限定的な業務例外: Discordチャンネル削除

退会そのものはDiscordのbot権限エラーがあっても完了させます。残存チャンネルのためにユーザーの退会を妨げないという業務判断であり、スライドの一般原則から意図的に外れる限定例外です。権限設定ミスを、捕捉したという理由だけでExpectedに読み替えてはいけません。

この例外を実装する場合は`Discordrb::Errors::NoPermission`だけを捕捉し、Rollbarへerrorとして報告します。channel IDとuser IDなど復旧に必要な識別情報を付け、トークンなどの秘密情報は含めません。退会処理は続行し、権限を直した後に残存チャンネルを削除する手順を示します。権限修正前の自動リトライループは作りません。

退会後も、残存チャンネルの対象情報を再取得・復旧できるよう保持します。既存の永続レコードで足りるならそれを使います。同じ原因をまとめても個々の対象は失わないでください。通知は既存のRollbar運用を使い、新しいメールや管理画面を必須にはしません。Rollbar項目を解決済みにするのは、権限修正と残存チャンネルの削除が両方済んだ後です。新しいジョブやテーブルは実装方法の一案であり、必須ではありません。
