# 設計判断: お知らせとイベント予定を認証付き読み取り専用APIで提供する

> この文書はproductionへの先行導入時点の判断を保存したものです。mainとの統合後の認証・設計方針は[ADR 0002](adr/0002-read-only-announcement-event-api.md)を参照してください。以下の「未導入」は先行導入時点の状況です。

- 状態: 提案中
- 日付: 2026-11-07

## 背景

外部の連携から公開済みのお知らせ一覧と、特別・定期イベントを統合した開催予定を取得したい。
検索APIでは公開日時や発生回を十分に表現できず、既存のICSは参加した定期イベントを中心とする別の用途である。
HTMLの詳細取得は足跡を記録するため、読み取り連携の代用にしない。

## 決定

`API::BaseController` を継承する一覧GETだけを追加し、既存のセッション・JWT・通常OAuth read認証、inactive拒否を保つ。
productionにはMCP認証とADR管理の枠組みが未導入のため、それらは取り込まず、この機能の設計判断だけを独立文書として残す。
お知らせはWIP・公開日時なし・未来公開を除外し、通知先分類のtargetを閲覧権限と解釈しない。
利用者・主催者・参加者の属性や足跡を追加しない。内部本文の読み取り権限を、公開画面への再配布許可にはしない。

予定取得は `API::EventSchedule` というPOROにまとめ、日付を検証してから最大31日だけ展開する。
定期の発生回計算には既存の `all_scheduled_dates(from:, to:)`、終了判定には `ended?`、休み表示には `UpcomingEvent#held_on_scheduled_date?` を再利用する。
特別イベントは期間との重なりと未終了を条件にし、前日に始まった開催中イベントを落とさない。
休みはダッシュボードと同様に表示するため、`held: false` を返し、一般的な取消状態には読み替えない。
発生回は種別・元ID・開始日時で識別し、開始日時・種別・IDで安定して並べる。

共通の `API::Pagination` がページ番号・サイズの文字列を厳密に検証する。既定20件、最大100件、ページ番号上限1,000,000とし、オフセットの際限ない拡大や巨大文字列の整数変換を避ける。
通常の不正入力には既存の400応答を使い、想定外の例外は捕捉しない。

## 検討した案

- 削除されたCRUD APIを丸ごと戻す: 今回は読み取りだけが必要で、書き込み権限と公開範囲の拡大を避ける。
- HTMLやICSをそのまま取得する: 足跡、対象範囲、WIPや休みの扱いが用途と一致しない。
- 日付ごとの `RegularEvent.scheduled_on_without_ended` を呼ぶ: 内部で `scheduled_on?` が既定の1年分を展開するため、検証した期間を明示して既存の計算メソッドを直接使う。
- 繰り返しルールをAPI側へ複製する: 祝日・ISO週番号・休みの仕様が画面と乖離するため採用しない。
- 休みの回を削除する: ダッシュボードの休み表示を再現できなくなるため採用しない。

## 結果・影響

既存の認証・予定計算に追従しながら、返却フィールド・期間・件数を制限できる。
予定は検証済みの期間内で統合・整列してからページングするため、対象イベント数に応じたメモリを使う。
大量データのストリーミングや更新間のスナップショット整合性は今回の契約に含めない。
既存モデル・HTML・ICSの仕様は変更しない。マイグレーションは不要。
