# 0004: 読み取り専用OAuthクライアントに更新トークンを限定する

- 状態: 採用
- 日付: 2026-11-13
- 採用日: 2026-11-13

## 背景

Classroomのような読み取り専用のサーバー連携では、7200秒で期限切れになるアクセストークンを継続的に更新する必要があります。既存のDoorkeeper設定は更新トークンを発行していません。すべてのOAuthクライアントに発行すると、書き込みやメンター・管理者権限を持つ既存クライアントにも長期間更新できる資格情報が増えます。

## 決定

Doorkeeper 5.8.2の`use_refresh_token`コンテキストブロックで、更新トークンの初回発行を限定します。環境変数`BOOTCAMP_REFRESH_CLIENT_UID`とUIDが完全一致し、confidentialかつMCP用でないapplicationであり、applicationの登録scopeと認可scopeの両方が`read`だけで、resource ownerを持つauthorization codeフローの場合に限って発行します。環境変数の未設定・空値・不一致では発行しません。public client、MCP用application（UIDを指定した場合も含む）、client credentialsフローでは発行せず、アクセストークンの有効期間と既存scopeは変更しません。

専用クライアントを明示的に指定し、共用のドキュメント保守用クライアントは流用しません。ポリシーは初回発行にのみ適用し、更新・失効処理にはDoorkeeperの標準実装を使います。コンテキストブロックは更新時には呼ばれないため、設定解除だけで既存更新トークンを止められるとは扱いません。解除時は対象の有効なトークンをすべて明示的に失効させます。

既存の`McpOauth::TokensController`でSorceryの`register_last_activity_time_to_db` after actionだけを除外します。ルートは変更せず、MCPのgrant・resource・redirect URI・owner検証、PKCE、認可ガードを維持します。MCP用でないクライアントは既存の早期returnにより、Doorkeeperの標準処理へ進みます。セッションなしの失効リクエストでは、このコールバックの`logged_in?`がSorcery JWTの認証を呼び、同名の`token`メソッドを持つDoorkeeperから`AccessToken`を受け取ってJWTのデコードで例外になります。OAuthのトークン処理をブラウザーでの利用者の活動記録から分離し、Doorkeeperの認証・発行・更新・失効・introspectionの処理は変更しません。

## 検討した案

- 全クライアントに更新トークンを発行する: 既存の高権限クライアントの資格情報も長期間更新できるようになるため、採用しません。
- アクセストークンの有効期間を延ばす: 期限切れ後の再認可という問題が残り、漏えい時の利用可能時間も延びるため、採用しません。
- 独自の更新・失効処理や失効フックを追加する: 標準の更新・失効処理と認証の保守範囲が増えるため、今回は導入しません。既存コントローラーへの変更は活動記録のコールバック除外だけに限定し、停止には標準の明示的な失効を用います。

## 結果・影響

専用の読み取り連携だけが更新トークンを新規取得でき、未設定では既存クライアントへの発行を増やしません。更新によるscope拡大はプロバイダーが拒否します。変更を有効にするにはBootcamp側のデプロイ、環境変数の設定、専用クライアントでの新しい利用者認可が必要です。

現在のスキーマには`previous_refresh_token`があり、Doorkeeperは更新後のアクセストークンの初回認証で旧トークンを失効させます。更新直後の旧更新トークンの再送は許容され、更新トークンには固定の有効期限がありません。連携側は更新を直列化し、新しいトークンの組の安全な保存と利用、停止時の失効を担当します。設定解除は新規発行の停止であり、既発行資格情報の失効とは別の操作です。
