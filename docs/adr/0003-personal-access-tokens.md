# 0003: APIの利用に個人アクセストークンを発行する

- 状態: 提案中
- 日付: 2026-11-12

## 背景

プラクティスの本文更新など一部のAPIは、DoorkeeperのOAuthアクセストークンと `write`・`mentor` などのスコープを要求します。`/api/session` のJWTやログインセッションでは利用できません。

これまでトークンを得る方法は認可コードフローだけでした。スクリプトやボット、AIエージェントからAPIを使うには、管理者がOAuthアプリケーションを作り、ブラウザーで認可し、コードをトークンに交換する必要があります。リフレッシュトークンは有効にしていないため、既定の有効期限（2時間）ごとにこの手順を繰り返すことになります。

ログイン名とパスワードだけでAPIを更新できるようにしたい、という要望がありました。

## 決定

メンターと管理者が、設定画面（`/current_user/access_tokens`）で個人アクセストークンを自分で発行・失効できるようにします。

- 実体は `Doorkeeper::AccessToken` とし、専用のOAuthアプリケーション「個人アクセストークン」に紐づけて保存します。APIの認証とスコープ判定は既存のDoorkeeperの仕組みをそのまま使います。
- `read` は常に付与し、`write`・`mentor`・`admin` は発行時に選びます。`mentor` はメンターと管理者、`admin` は管理者だけが選べます。
- 有効期限は30日・90日・365日から選びます。無期限のトークンは発行しません。
- トークンの値は発行直後の画面でだけ表示し、flashやセッションには載せません。一覧にはスコープ・発行日時・有効期限だけを表示します。
- 対象をメンターと管理者に限るのは、現時点でスクリプトからのAPI利用が必要なのがこの範囲だからです。

## 検討した案

- **リソースオーナーパスワードクレデンシャルグラント（`grant_type=password`）**: ログイン名とパスワードを直接トークンに交換できますが、RFC 9700で使用が禁止され、OAuth 2.1では削除されています。パスワードをスクリプトや設定ファイルに置くことになり、漏れた場合にスコープで被害を絞れないため採用しません。
- **`/api/session` のJWTで書き込みも許可する**: パスワードグラントと同じ問題があり、スコープによる制限もなくなるため採用しません。
- **デバイス認可グラント（RFC 8628）**: CLIからの利用体験はよいものの、gemの追加と承認画面が必要で、今回の用途には大きすぎます。
- **リフレッシュトークンを有効にする**: 再認可は減りますが、初回のOAuthアプリケーション作成とブラウザーでの認可手順は残ります。既存のトークンの挙動にも影響します。
- **トークン用のテーブルを新設する**: 名前や最終利用日時を持てますが、認証の仕組みが二重になります。まずは既存のテーブルを使い、必要になった時点で検討します。

## 結果・影響

- メンターと管理者は、OAuthアプリケーションを用意しなくてもAPI用のトークンを取得できます。
- パスワードをスクリプトに渡す必要がなく、漏れた場合はそのトークンだけを失効させられます。
- `oauth_access_tokens` に名前の列がないため、トークンにラベルは付けられません。一覧ではスコープと日時で見分けます。
- トークンは既存のOAuthトークンと同じく平文で保存されます。ハッシュ化（`hash_token_secrets`）は既存トークンの扱いも変わるため、この判断の範囲外とします。
- 専用のOAuthアプリケーションは名前で特定します。管理画面でこのアプリケーションの名前を変更したり削除したりすると、発行済みトークンが一覧に出なくなる、または無効になります。
- 最長365日の長期トークンが存在するようになります。不要になったトークンは利用者が失効させる運用とします。
